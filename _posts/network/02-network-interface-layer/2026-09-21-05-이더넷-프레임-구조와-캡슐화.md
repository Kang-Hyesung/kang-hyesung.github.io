네트워크 계층에서 내려온 IP 패킷은 그대로 물리 매체로 전송되지 않는다. 데이터 링크 계층은 현재 링크에서 전달하는 데 필요한 헤더와 트레일러를 붙여 **프레임(Frame)**을 만들고, 수신 측은 이를 검사한 뒤 원래의 패킷을 꺼낸다.

이 글에서는 현재 LAN에서 널리 사용하는 Ethernet II 프레임을 기준으로 캡슐화와 역캡슐화, 헤더 필드, 프레임 크기와 FCS의 역할을 살펴본다.

## 패킷을 프레임으로 만드는 캡슐화

송신 측 데이터 링크 계층은 인터넷 계층에서 받은 IP 패킷을 페이로드로 넣고 Ethernet 헤더와 FCS 트레일러를 추가한다.

```mermaid
flowchart LR
  packetIn["송신 측<br/>IP 패킷"]
  frame["Ethernet 프레임"]
  packetOut["수신 측<br/>복원된 IP 패킷"]

  packetIn ==>|"헤더·FCS 추가<br/>캡슐화"| frame
  frame ==>|"주소·FCS 검사 후<br/>역캡슐화"| packetOut

  classDef network fill:#14532d,stroke:#4ade80,stroke-width:2px,color:#f8fafc
  classDef frameStyle fill:#164e63,stroke:#22d3ee,stroke-width:2px,color:#f8fafc

  class packetIn,packetOut network
  class frame frameStyle
```

- **캡슐화(Encapsulation)**: 상위 계층 데이터에 현재 계층의 제어 정보를 붙이는 과정이다.
- **역캡슐화(Decapsulation)**: 수신한 프레임을 검사하고 헤더와 트레일러를 제거해 페이로드를 상위 계층으로 전달하는 과정이다.

## Ethernet 프레임의 필드

현재 LAN에서 널리 사용하는 VLAN 태그 없는 **Ethernet II 프레임**은 다음 필드로 구성된다.

| 순서 | 필드 | 크기 | 역할 |
| :--- | :--- | :--- | :--- |
| 1 | 목적지 MAC 주소 | 6바이트 | 현재 링크에서 프레임을 받을 인터페이스 식별 |
| 2 | 출발지 MAC 주소 | 6바이트 | 프레임을 보낸 인터페이스 식별과 스위치 학습에 사용 |
| 3 | EtherType | 2바이트 | 페이로드에 들어 있는 상위 프로토콜 식별 |
| 4 | 페이로드 | 46~1500바이트 | IP 패킷이나 ARP 메시지 등 운반할 데이터 |
| 5 | FCS | 4바이트 | CRC 계산으로 전송 중 프레임 손상 여부 검사 |

목적지·출발지 MAC 주소와 EtherType을 합친 **Ethernet 헤더는 14바이트**다. EtherType의 대표적인 값으로 IPv4는 `0x0800`, ARP는 `0x0806`, IPv6는 `0x86DD`를 사용한다. 수신 장치는 이 값을 보고 페이로드를 어떤 프로토콜 처리기로 전달할지 결정한다.

FCS(Frame Check Sequence)는 프레임 끝에 붙는 트레일러다. 송신 측은 프레임 내용으로 CRC 값을 계산해 기록하고, 수신 측은 다시 계산한 값과 비교한다. 값이 다르면 프레임이 손상된 것으로 판단해 폐기한다.

## 64바이트부터 1518바이트까지

VLAN 태그 없는 Ethernet II 프레임의 크기는 목적지 MAC 주소부터 FCS까지 **64~1518바이트**다.

```text
최소 크기 = 헤더 14 + 최소 페이로드 46 + FCS 4 = 64바이트
최대 크기 = 헤더 14 + 최대 페이로드 1500 + FCS 4 = 1518바이트
```

상위 계층 데이터가 46바이트보다 작으면 최소 프레임 크기를 맞추기 위해 패딩을 추가한다. 흔히 말하는 Ethernet의 **MTU 1500바이트**는 전체 프레임 크기가 아니라 페이로드로 운반할 수 있는 네트워크 계층 데이터의 일반적인 최댓값이다.

> 위 크기에는 물리 계층의 동기화를 위한 7바이트 프리앰블과 1바이트 SFD, 프레임 사이의 간격은 포함하지 않는다. `802.1Q` VLAN 태그를 넣으면 프레임에 4바이트가 추가되어 일반적인 최대 크기가 1522바이트가 된다.
{: .prompt-info }

Ethernet 이외의 Wi-Fi, PPP 같은 데이터 링크 기술도 프레임을 사용하지만 헤더 구성과 주소 필드, 오류 처리 방식은 서로 다르다. 따라서 모든 데이터 링크 프레임에 Ethernet 헤더가 붙는다고 일반화하면 안 된다.

## 수신 측의 역캡슐화

수신 장치는 물리 계층에서 복원된 비트열을 프레임으로 해석한 뒤 다음 과정을 수행한다.

1. 프레임의 경계와 형식이 올바른지 확인한다.
2. 목적지 MAC 주소를 보고 자신이 처리해야 하는 프레임인지 판단한다.
3. FCS를 다시 계산해 전송 중 프레임이 손상되었는지 검사한다.
4. EtherType으로 상위 프로토콜을 확인한다.
5. 헤더와 트레일러를 제거하고 페이로드를 IPv4, IPv6, ARP 등 알맞은 처리 대상으로 전달한다.

이 과정은 헤더와 트레일러를 무조건 제거하는 작업이 아니다. 주소와 오류 검사를 통과하고 상위 프로토콜을 식별한 뒤에야 페이로드가 다음 계층으로 전달된다.

## 오류 검출과 오류 수정은 구분해야 한다

데이터 링크 계층이 오류를 처리한다고 해서 모든 링크 기술이 손상된 프레임을 직접 수정하거나 재전송을 요청하는 것은 아니다.

일반적인 유선 Ethernet은 송신 측이 프레임 내용으로 CRC 값을 계산해 FCS에 넣고, 수신 측이 같은 계산을 수행해 값이 일치하는지 확인한다. 값이 다르면 전송 중 비트가 변한 것으로 판단해 프레임을 폐기한다. Ethernet 자체에는 해당 프레임을 다시 보내 달라는 확인 응답과 재전송 절차가 없다.

반면 Wi-Fi 같은 일부 데이터 링크 기술은 무선 환경의 손실을 보완하기 위해 링크 계층 확인 응답과 재전송을 제공한다. 오류 정정 코드로 일부 오류를 복구하는 물리·링크 기술도 있다. 최종적인 신뢰성은 TCP 같은 상위 계층이나 애플리케이션이 추가로 보장할 수 있다.

> Ethernet의 FCS는 오류가 발생했는지 높은 확률로 검출하기 위한 값이지, 손상된 원래 데이터를 복원하는 정보는 아니다. `오류 검출`, `오류 정정`, `재전송`은 서로 다른 기능이다.
{: .prompt-warning }

## 정리

- 송신 측은 IP 패킷에 Ethernet 헤더와 FCS를 붙여 프레임으로 캡슐화한다.
- Ethernet 헤더는 목적지 MAC 주소 6바이트, 출발지 MAC 주소 6바이트, EtherType 2바이트로 구성된다.
- 페이로드는 일반적으로 46~1500바이트이며 부족한 크기는 패딩으로 채운다.
- VLAN 태그가 없는 Ethernet II 프레임은 기본적으로 64~1518바이트다.
- MTU 1500바이트는 전체 프레임이 아니라 네트워크 계층 데이터를 담는 페이로드의 일반적인 최댓값이다.
- 수신 측은 주소, FCS와 EtherType을 확인한 뒤 페이로드를 역캡슐화한다.
- FCS는 오류를 검출하지만 손상된 데이터를 수정하거나 재전송하지는 않는다.

Ethernet 프레임 구조를 이해하면 IP 패킷이 같은 링크를 통과할 수 있는 형태로 어떻게 포장되고, 수신 측에서 어떤 검사를 거쳐 다시 상위 계층으로 전달되는지 설명할 수 있다.
